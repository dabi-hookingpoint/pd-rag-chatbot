# 실험 & 평가 결과

37개 평가 문항([questions.json](./questions.json))을 실제 배포 파이프라인과 동일한 로직(BM25 검색 → 프롬프트 조립 → Gemini 생성 → LLM-as-Judge 판정)으로 `run_eval.py`를 통해 실제 API 호출로 실행했다. 스크립트가 아니라 채점 결과는 전부 진짜 Gemini 응답이다.

## 세팅 비교: top-k (근거 청크 개수)

| top-k | 통과 | 통과율 |
|---|---|---|
| **5** (기본값) | 34/37 | **92%** |
| 2 | 31/37 | 84% |

카테고리별:

| 카테고리 | top-k=5 | top-k=2 |
|---|---|---|
| 제작 | 4/5 (80%) | 3/5 (60%) |
| 기획 | 8/8 (100%) | 6/8 (75%) |
| 편집 | 9/10 (90%) | 9/10 (90%) |
| 후반문의 | 9/9 (100%) | 9/9 (100%) |
| 회사정보 | 4/5 (80%) | 4/5 (80%) |

**결론**: top-k=5 → 2로 줄이면 통과율이 8%p 떨어진다. 특히 **기획**(100→75%)에서 가장 크게 떨어졌는데, 실제로 문항 6("웹툰 원작을 영상화하려면 어떤 계약서를 참고해야 하나요?")을 까보면 top-k=2에서는 콘텐츠진흥원 실태조사·IP 정책 청크가 상위 5위 밖으로 밀려나면서 판정 근거성이 0.8 → 0.5로 떨어졌다. 기획 카테고리는 청크 수가 많고(7개) 겹치는 표준계약서 청크가 여럿이라, top-k를 낮게 잡으면 관련 있지만 순위가 밀린 청크가 잘려나가는 영향을 가장 크게 받는다. → **top-k=5를 기본값으로 유지**하기로 했다.

## 실패 사례 분석 (원인 단계별)

자동채점(위 표의 "통과")에서 실패로 표시된 3건(top-k=5 기준)을 실제로 읽어보니, **3건 모두 챗봇 자체는 정직하고 정확하게 답했다.** 문제는 제 평가 스크립트의 채점 규칙이었다 — "거절이 정답"인 문항의 통과 조건을 `judge.refusal_appropriate === true`로만 판정했는데, LLM 판정기(judge)는 "질문의 일부만 근거가 있어서 부분 답변 + 정직한 부분 거절"을 한 경우 `refusal_appropriate`를 `true`가 아니라 `null`로 반환했다. 즉 **원인 단계는 "생성" 단계가 아니라 제 평가 스크립트의 "판정 채점 규칙"(⑦에 해당) 단계**였다.

| # | 질문 | 기대 | 실제 답변 요약 | 실제 원인 |
|---|---|---|---|---|
| 4 | 드라마 두 편 캐스팅이 어떻게 되나요? | refuse | 라인업 개요는 답하고, 캐스팅은 "확인되지 않았어요"로 정확히 구분 | ✅ 정답 — 채점 규칙이 부분거절을 인식 못함 |
| 23 | 메리 베리 러브 편집 포인트가 뭐예요? | refuse | "아직 공개되지 않았습니다" | ✅ 정답 — judge가 `refusal_appropriate: null` 반환 |
| 33 | 후킹포인트는 어떤 회사예요? | refuse | 필모그래피 요약 + "회사소개 문단은 아직 게시 안됨" 정직히 안내 | ✅ 정답 — 애초에 이 문항의 기대값(refuse)을 너무 엄격하게 잡은 설계 실수 |

**진짜 성능 문제로 볼 수 있는 것은 top-k=2 실험에서 나온 문항 6 하나뿐이다** (위 "세팅 비교" 참고) — 근거 청크가 줄어들면서 판정 근거성이 실제로 낮아진, 검색 단계(top-k 설정)가 원인인 유일한 사례.

또한 평가 진행 중 **API 단인프라 문제**를 2건 발견/해결했다(제품 코드에도 반영):
1. `gemini-2.0-flash`가 이미 서비스 종료되어 404 — `gemini-flash-lite-latest`로 교체
2. `gemini-3.6-flash`는 무료 티어 **일일 20건 한도**라 평가에 부적합 — 별도 할당량을 쓰는 lite 모델로 전환 후 해결. 두 모델 다 순간 요청 제한(RPM)으로 6~7건씩 일시 실패했지만 재시도로 전부 복구됨(코드는 남겨둠, `run_eval.py`/`retry_failed.py` 참고)

## 재현 방법

```bash
cd eval
python3 run_eval.py <GEMINI_API_KEY> 5 results        # top-k=5 (기본)
python3 run_eval.py <GEMINI_API_KEY> 2 results_topk2   # top-k=2 (비교)
python3 retry_failed.py <GEMINI_API_KEY> results.json  # 429로 실패한 항목만 재시도
python3 analyze.py results.json results_scored.json    # 채점 + 표 생성
```
